    所有的 dev 分支都是当前重要的分支，其中: 
      - dev/QA-1104 是工标知识问答的开发分支
      - dev/hazard-1104 分支是隐患识别的主要分支
      - dev/20261025 则是开发分支中的主要合并分支

    也就是说如果工标知识库问答和隐患识别都做完了，最终是先合并到 dev/20261025 上

    当前暂时不存在一条独立的施工方案审查的分支，后续阅读代码的时候也需要注意，这将会是接下来的主要工作目标

    当前大致的层级关系可以梳理成:

    #+begin_src Markdown

    Vue 控制台 / 对外 API
        ↓
    agent-server：HTTP、会话、存储和能力装配
        ↓
    agent-core：Pi 会话行为、运行约束和路由(agent-firewall)
        ↓
    agent-tools：按预设挑选工具
        ↓
    *-core：部分业务的确定性判定规则
        ↓
    domain-*：执行某项业务能力

    #+end_src

    但是 *-core 和 domain-* 层级相对混乱,基本上不能单纯的用 DDD 或者六边形架构的视角去理解它们
    但是从设计初衷上来看,是希望 *-core 层级承担核心代码,而在 domain 层级上做业务编排
    但是由于有的时候这两个层级会有互相覆盖的清况,所以可能会有的时候有 core 没有 domain,有 domain 没有 core

    另外,电力施工方案审查似乎还没有完全做完,所以这也应该是只有 domain-power 而没有 power-core 的原因

    除了这些主要的和 Agent 相关的模块,还有其他的模块: platform-db, domain-web, shared-types, ui-components
    platform-db主要的服务对象是 apps 的 agent-server, 他负责所有的和数据库(SQLite)的管理和控制, domain-web
    封装了 web-search/web-fetch, shared-types 是契约, 对各个层级有契约约束, 本身不依赖任何其他 packages 等,
    ui-components 是控制台的通用 Vue UI 组件库, 服务于 apps/web-console, 本身也不依赖其他 packages.

    担忧:
    在电力施工方案审查里面,给 Agent 开放的工具包含了 write, bash, PowerShell,而 pi 本身没有执行审核,这意味着,
    有一个拥有可读可写可执行权限的 Agent,不经过审核就可以去自主完成任务,一旦收到攻击,write 和 bash 很容易被当作
    目标,后果可能很严重
