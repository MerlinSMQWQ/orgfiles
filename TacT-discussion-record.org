* 讨论的起点与当前决定

TacT（Thinking and Collaboration Toolkit）的起点，是 tact 这个词里人与人协作的分寸感。Merlin 希望它逐步承载自己的工程思想：人能够自然且深入地参与，Agent 能作出有依据的工程判断，项目仍然交付可以使用、理解和维护的成果。人的交互体验与高质量交付同等重要。

这份记录按主题整理对话，保留观点如何修正。Merlin 的价值选择、仓库写明的约定、已经执行的检查、Claude 的评审意见和 ChatGPT 的建议分别归属各自的来源。除明确加引号处，均为转述。讨论中没有找到能确认 Merlin 更早就完整讲过这套约束观的记录；此前 TacT 的名称和定位则是明确的。

** 此刻已经有依据的结论

当前基线是 [[https://github.com/MerlinSMQWQ/TacT/tree/6cb61ef0406880c539c150aeb6e86a4e24e03f4d][v0.1.3 对应的提交 6cb61ef]]。现版已经写有人的主动参与、目标优先、项目规则的授权和退出。安装器与测试提供的是文件层面的证据。在一个边界清楚的文档修正任务中，使用 TacT 和最小入口的两组都完成了任务，未观察到交付上的额外收益。人的真实体验、复杂判断上的效果、专题是否经常读得过多，仍待观察。

上轮已有一份未推送的可选文档补丁。另有一个已复现的换行兼容问题。运行时规则是否改、是否做 v0.2 整体原型、是否发布或要求采用项目迁移，均未决定。本次要求是先留下文档，再讨论检验办法；它不构成启动优化的确认。

* 共享原则与项目规则

** 弱约束怎样约束判断

Merlin 希望跨项目共享的是判断依据。所谓“弱”，主要指对具体动作预先规定得少。例如，验证投入应与失误后果相称：一个可随时重做的小改动，和改变外部承诺的共享组件，可以合理地接受不同的验证。如果一条原则既能赞成所有选择，又不能帮助说明任何取舍，那么它即使很稳定，实际约束力也有限。

项目强规则保存特定条件下已形成的约定。公共 SDK 承诺兼容时，需要维护旧接口；没有兼容承诺的内部原型则可以直接替换试验接口。不同项目得出相反结论不构成矛盾。值得保存的还有规则服务的目标和成立条件，方便以后判断何时收窄、替换或退出。

** 谁能改变规则

人掌握项目规则的决定权。Agent 可以发现冲突、整理理由，并按人的指导或预先授予的权限维护规则。一次 demo 获得例外，不等于正式项目从此改变约定；执行任务的权限，也不能自动扩大为取消妨碍该任务的规则的权限。维护既包括增加，也包括合并、删除和保留已注明失效条件的历史解释。

Merlin 使用过“取消全局强约束”的表述。现版仍把授权、数据完整性、如实报告等列为跨项目边界。讨论中提出的一种协调解释是：取消跨项目统一的刚性执行流程，同时保留共同责任边界。这是对术语的候选澄清，不能替 Merlin 宣布为最终定义。

* 人如何参与并掌控项目

** 从监督和纠偏到共同形成成果

最初的回答把人主要放在监督执行、纠偏、控制规则的位置。Merlin 随后澄清：即使 Agent 能独立完成某项工作，人也可能愿意一起设计、试用、讨论或亲自写一部分。这些参与有独立价值。所谓“无感”，是注意力可以停留在正在解决的问题上，一句自然的反馈就能进入工作，不必先切换成管理工具的人。

例如，看到原型后说“已发出去的请求让它完成，不再启动下一步，已有结果保留；按钮文案我来”，同时澄清了产品语义、验收重点和实施分工。这是设计示例，不是已观察到的用户试验。一场深入讨论可能比连续点击几次确认更轻松；少发消息不能单独证明体验改善。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/core/collaboration.md#L13][现版协作指南]]已经表达了这种参与的价值。

** 知道文件位置与理解项目

领导强调使用 AI 应知道改哪些文件、项目如何组织、实现方式和原理。Merlin 认可这些知识的价值，更看重宏观目标一致、微观实现灵活，以及“对还是不对，并有确切依据”。执行前尚未确定文件，与交付时解释不清关键影响，是不同情况；需要的理解深度取决于人要承担的维护、审查和排障责任。

划分宏观与微观时要看影响：几行重试或权限代码也可能承载重要承诺。运行样例能证明已观察场景；契约测试检验特定性质；关键 diff 和路径解释帮助审查设计。实现和测试若出自同一误解，全部通过仍可能偏离人的目标。掌控包括能在需要时追溯证据、辨认哪些判断尚未成立，并及时改变方向。

** 为什么实践空间重要

Merlin 希望实践，也害怕自己错；公司不愿让他这样试，使“愿意接受检验”和“有机会检验”之间出现落差。当前谁决定工作方式，与长期哪种方法有效，是两个问题。换团队是考虑过的选项，没有成为离职决定。了解别的团队时可以问一次真实分歧怎样处理、最近一次尝试怎样改变规则；不必把团队级验证的负担转嫁给个人休息时间。[[https://dora.dev/capabilities/team-experimentation/][DORA 对团队试验条件的说明]]提供了组织层面的参照。

* 观察变化的理论工具

** 敏捷和目标

Merlin 以敏捷为核心，重视动态平衡、对立统一、拥抱变化、简化流程，以及“锚定目标，不要被过程异化”。[[https://agilemanifesto.org/iso/zhchs/manifesto.html][敏捷宣言]]强调可工作的软件与人的互动，承认文档、流程和计划也有价值；[[https://agilemanifesto.org/iso/zhchs/principles.html][其原则]]也重视良好设计、技术质量与反思。记录为何保留某项外部承诺，可能比复述代码有用。相同的提醒也适用于 TacT 自己：如果拼命证明整套理念正确开始妨碍工作和理解，就应当重新考虑验证方式。

** 状态机和马尔可夫视角

Merlin 曾用 Guix 说明这种直觉：从已知状态出发，借助适当操作到达预期状态。工程中可区分目标状态、允许的动作、需要保持的性质及实际转移。状态图允许多条路径、回退和分支。马尔可夫性还有更强的条件：已知当前状态后，更早的历史不再改变下一状态的条件分布。采用“状态”这个词不会自动满足这一条件。[[https://ocw.mit.edu/courses/res-6-012-introduction-to-probability-spring-2018/f02929e77a4e43c43c97fcd78d114674_hsQnmrHbbms.pdf][MIT 关于马尔可夫性的说明]]

两个任务同样显示 failed：一个尚未写入，另一个已经写入、只是回执丢失。若重复写入有副作用，二者不应盲目采用相同的重试策略。此处要追问的是实际状态、可见证据，以及不同答案是否会改变行动。控制论的[[https://www.cds.caltech.edu/~murray/FBS/Output_Feedback.html][可观测性]]启发我们区分可直接测量的输出与需要推断的内部状态；工程类比不能代替数学模型对可观测性或稳定性的证明。

** 理论和历史能给工程什么

Merlin 反对把工程归结为经验，把计算机专业归结为操作训练。经验提供情境判断；理论让假设、边界和未经历过的情形可讨论；实践又修正两者。历史值得研究的是：当时的成本、工具和分工如何塑造问题，某种抽象解决了什么，又把困难移到哪里。[[https://pages.cs.wisc.edu/~remzi/Naur.pdf][Naur 关于编程与理论形成的论文]]讨论开发者解释、维护系统的理解；[[https://www.cs.utexas.edu/~EWD/transcriptions/EWD03xx/!SV-EWD340.html][Dijkstra 的 The Humble Programmer]]讨论机器能力提高后问题规模也在变化。Agent 杠杆还有多少空间是探索方向；理解计算机原理的价值也无需只靠立即提高产量来证明。

* 仓库已经做到什么

** 安装边界与已有原则

TacT 通过 Python CLI 安装本地 Markdown 快照，根 AGENTS.md 引用 .tact/AGENTS.md 与项目 notes；.tact/core/ 是共享专题，.tact/project/ 归采用项目所有。项目可有同名专题补充；另有一个薄的项目级 skill 指向同一快照。init 和 refresh 都有预览，安装记录保存包版本与共享文件的字节哈希。项目可选不同版本。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/core/README.md][采用说明]]

[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/core/working.md#L23][目标与计划]]、[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/core/collaboration.md#L15][主动参与]]、[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/core/evolving.md#L15][规则退出]]均已写入。项目 notes 区分观察、假设、建议和已确认要求；一个项目出现的经验不能未经检验就成为其他项目的义务。仓库约定运行时使用英文，保留入口、专题与项目层，不预设评测平台、每专题一个 skill 或强制项目字段。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/project/notes.md][源仓库的项目约定]]

** 文本存在与行为有效之间的距离

迁移记录保留了完整英文基线和一次找回正确来源的真实排查，并报告过在源仓库根目录检查 Codex CLI 启动输入；该次输入检查没有调用模型，notes 仍须显式读取。此前评审从 6cb61ef 构建 sdist 和 wheel，在独立环境安装该 wheel 后跑通 28 项测试。它们支持文件操作与打包结论，不能证明新会话能稳定阅读、选择正确，或让人更愿意参与。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/docs/migration.md#L63][迁移证据及其边界]]；[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/project/verification.md#L5][验证口径]]。

入口对准备实质工作、选择验证范围、写交付说明的触发可能重叠。入口加 working、verification、communication 三篇，共 5,048 个按空白计数的词、34,874 字节，不含项目补充。这是潜在阅读量，不是 token 数或实测延迟。专题允许按需复用，不应直接推断每次都会全读。只有读了什么、为什么读、是否改变判断的真实记录，才能帮助决定要不要收窄索引。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/AGENTS.md#L37][阅读索引]]

* 已复现的问题与迁移边界

** Git 换行与刷新冲突

此前在 Linux 上初始化并提交项目，再用 core.autocrlf=true 克隆；主评审检查 git status --porcelain 为空，同一版 refresh --dry-run 仍退出 1，并报告 13 个共享文件不匹配。Git 改变了工作树行尾，而 manifest 按原始字节计算和比较 SHA-256。仅为现有共享路径及 manifest 指定 text eol=lf 后，同样的干净克隆预览报告已是最新。该结果不是 Windows 实机测试。已有[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/tests/test_cli.py#L140][换行差异保护测试]]；建议给出范围明确的 LF 配置和诊断，不仅凭字节差别推定来源或覆盖用户编辑。

** 预览截断与一次对照

[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/src/tact/cli.py#L69][show_diff]] 对每个文件最多展示 60 行 diff，包括头部和上下文，超出会给出截断提示。正式刷新使用完整的计划内容。原 README 称会展示全部差异，容易让人误以为漏写；曾讨论过完整 diff 选项，候选补丁只修文案，不增加 CLI 参数。

此前两个隔离会话面对同一真实问题、同一源码与包：一组根入口为 TacT，另一组为最小指引；两组都被要求读取入口。两组都报告复现“预览省略、实际完整写入”，随后收到同一句模拟反馈“保留摘要，不加参数，只改英文 README”。主评审核对了最终 diff：两组都只改 README，且都说清上述区别。每组一次，没有测到该任务上额外的交付收益；未验证自动加载、人的亲身体验，也不能推出 TacT 一般无效。

** 调整布局和文件所有权

模拟未来改写安装器嵌入根 AGENTS.md 的标记块，或删除旧 manifest 中的共享专题，都会触发当前 refresh 的保护并停止；这是候选升级路径模拟，不是已发布的 0.1.2 到 0.1.3 升级事故。共享 .tact/AGENTS.md 与根标记块不是同一文件。已有项目的 project/README.md 通常保留，只有精确匹配已知生成模板的 notes 可能自动更新，不能把新的通用说明只放在项目文件里却期待所有旧用户收到。[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/src/tact/cli.py#L84][入口检查]]；[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/src/tact/cli.py#L156][manifest 与文件计划]]。

另有两个较小的问题：手动采用说明将 notes 写成按需创建，入口却要求必读，可统一成“无文件则创建，无约束则保持最小”。POSIX 临时目录实测：若根 AGENTS.md 与目录外文件是硬链接，需要追加入口时，另一名称下也能看到改动；它不同于绕过符号链接检查，是低频、具体的共享文件语义。

* Claude 评审及逐项判断

以下是外部评审和随后形成的建议，不代表 Merlin 已批准改动。

** 一 统一状态模型

Claude 将状态模型视为最大缺口，建议规定状态、转移和报告形式。采纳“让会改变决定的状态看得见”，保留对统一模型的判断。现有材料未证明人普遍需要从长报告里拼出状态。状态足够预测某一步，也不等于人有权、有信息且来得及介入。可先在一次取消、重试或恢复判断中观察具体混淆。

** 二 平衡原则的取舍信号

部分采纳。现版已有判据：尝试不产生新证据时换方法；只有不说明便会影响决定的限定才应保留。应区分“缺少判据”和“判据难以找到”。业务行为变化也不自动要求停下来请示：已授权的目标可以执行，缺少人的意图、授权或重要取舍时，再把问题交还给人。

** 三 运行指导与思想记录

选择性拆分。删除某段理由若会改变边界情形下的行动，它应留在原则旁；只解释思想形成或迁移过程的材料，可以另存设计记录。把所有 Why 段一律移走，可能使弱原则失去适用条件。专题篇幅大也不能直接推出人的汇报阅读负担大。

** 四 分发投入与核心验证

赞成优先观察真实协作。“已被过程异化”是提醒，尚非事实诊断。CLI、manifest 和 refresh 在[[https://github.com/MerlinSMQWQ/TacT/blob/6cb61ef/project/notes.md#L13][项目记录]]中有明确采用动因。建议暂停无具体采用问题的分发扩张；对已复现的 CRLF 障碍仍可独立处理。少数任务用来定位问题，不能证明普遍收益。

** 五 项目规则的退出

撤回“只能添加、不能退出”的事实诊断。已有授权维护、修订、合并和删除机制。可检验的问题是：一次例外有没有影响下一次任务；授权结束后，旧规则是否还在支配行动。

** 六 首页 宿主与英文表达

建议首页先展示人怎样改变成果，把发布流程移到维护者文档。Codex 有特定启动路径的证据；其他宿主未见等价检查，不等于不兼容。英文运行文本是既定选择，表达“无感参与”宜写可见行为，例如 developers can shape the work as their understanding changes，再给出例子。尚无理由按哲学术语逐个建设宿主适配或全局术语表。

* 迭代路线与版本决定

** 已有候选交付

[[https://chatgpt.com/library?file_id=libfile_fa931f1ba01c8191b118b368dcb329d4&account_id=personal][上一轮可选文档补丁]]基于 6cb61ef，已通过 git apply --check，未推送。它在 README 中加入开发者试用中改变停止语义、接手按钮文案的示例，将发布说明移至 docs/releasing.md，更新已发布包的安装措辞、预览截断说明及已记录的宿主验证范围。示例没有被当成真实用户访谈。手动采用的 notes 矛盾、CRLF 诊断和运行时更改不在该补丁内。

** 小步优化方案

P1 是观察真实判断，必要时修改一个索引触发或一条判据；P2 是改善首页与采用说明；P3 是独立处理 CRLF。计划的停止点是有证据说明应保留、调整还是暂缓。若只发现工具限制，修工具；若没有可归因的规则问题，允许不改运行时。专题读得过多、读错了专题、读了仍做错，不能使用同一种修法。

** 为什么也可以设计大版本

谨慎更新的理由有三点：现有机制已经覆盖一部分需求，尚未证实主要问题在结构；同时更改索引、状态表达和汇报方法，难以归因到其中一项；删改专题会产生迁移成本。这些理由支持保留基线和慎重替换默认，并不要求在做出原型之前先证明原型有效。

如果体验依赖多个机制共同出现，可以在独立分支设计一套完整的 v0.2 候选：人的一句新判断怎样自然改变实现、验证与分工，同时保留仍有效的约束。用 v0.1.3 作参照，允许整体比较；若整体更好，不据此断言每个组件都有效。结构性探索、替换默认、发布 v1.0 和承诺长期兼容，是四个可分开作出的决定。

** 仍由 Merlin 决定

要不要开 v0.2 原型、先选哪项真实工作、哪些体验值得投入和何时采用新默认，均不由实验代替决定。希望有实践机会与害怕自己错可以同时成立；让方法接受修正，本身就在贯彻“锚定目标”。这份纪要没有批准任何版本路线。

* 先验证问题是否发生

** 从一个需要你重新介入的时刻开始

优先问题建议：当 Merlin 看了中间成果，用一句普通的话改变目标或分工，当前协作能否让这句话进入下一步实际行动？从手头已有任务中找一个这样的时刻，不要求为试验另开项目。可用个人项目或已获授权的工作片段；如果没有任何实际困扰，可以先保留这条假设。

最有用的原材料很少：当时看到的中间结果、你说的原话、你预期随之改变和应保持不变的部分、Agent 的下一步动作，以及最终可核对的差异。可以在行为发生前为自己记半句预期，减少看完结果再改标准的倾向。它是个人复盘用的简记，不应成为所有任务的汇报协议。

** 怎样判定一次具体失配

以停止任务为示例：如果你明确要保留历史结果，之后的 diff 或运行结果却删除了它，就有一次行为偏差；如果你接手按钮文案而 Agent 又覆盖它，就有分工偏差。如果行为正确，而你不得不重述它已经知道的要求三次，结果达标、体验仍有损耗。反过来，你主动要求多聊几轮实现原理，这种投入可能正是你希望保留的体验。

人是否需要重复说明，可以查对话；功能是否落实，看 diff、测试或运行结果；你是否被打断、愿不愿意这样配合，只能由你评价。可以问自己两句：“哪次交流让我改变或澄清了判断？”“哪次交流只迫使我管理工具？”一次真实失配足以证明它在该情境发生过，还不能说明它常见，或归因于 TacT。

** 也可以检验对项目的掌控

在看实现前，先指出这次改动要保持的行为、最可能破坏哪项承诺，以及什么现象会使你判定它有错；交付后再追到实际 diff 或运行结果核对。若你能识别关键偏差、解释证据并在必要时接手，这比能否预报文件名更贴近你的定义。若证据全由 Agent 自述，或者你不能解释哪种结果会推翻自己的判断，就暴露出了应当补足的理解。一次任务不用于给自己或领导的能力排名。

** 第二个可选案例

若近期恰有规则变动，可以观察“这次 demo 允许改接口”与“从这个版本起不再承诺旧接口，并更新项目约定”。前者只改变本次范围，后者在明确授权下才形成长期约定。检查本次行动之外的下一项任务和项目 notes，才能看出一次例外有没有泄漏。没有改 notes 的授权时，提出建议即可。不要为了凑案例制造新的审批步骤。

* 从观察到对照和决定

** 先找故障发生在哪一层

规则没有进入上下文：检查入口、实际读取轨迹和项目 notes 的可见性。规则进入了，仍选错动作：回到决策当时，看是否缺少区分两种状态的证据、业务意图或取舍信号。判断正确但没有落实：检查工具、权限、外部依赖及执行反馈。只看到文件被打开不能证明应用正确；工具阻塞也不该被修成越来越长的提示词。

每次尽量保留一个竞争解释。比如你重复了一次要求，既可能是 Agent 遗漏了上下文，也可能是你看了原型才形成新的要求。回看原话和中间成果，可以把“补救”和“共同设计”区分开。若材料不足，记录“原因未确定”，不把推测写成项目强规则。

** 想回答哪个问题 就选哪组对照

“现有 TacT 在这个情境是否有用”：比较最小入口与 v0.1.3，两组保留同一份项目硬约束、授权、代码起点和验收条件。“某个改动是否解决刚发现的问题”：比较 v0.1.3 与一项候选改动。“完整 v0.2 是否给出更好的整体体验”：允许多个设计一起变，但结论只到整体方案。两个不同任务不能各自充当另一任务的对照。

尽量保持宿主、模型设置、起点和工具可用性相近。Merlin 只需自然参与其中一次，另一组可以重放同一句反馈；重放能检查后续行为，不能复制第一次形成意图的体验。若希望比较两种体验，可日后在两次相近的真实工作中分别尝试，保留任务差异、熟悉度和顺序影响，不用假装是严格盲测。

** 什么时候停止

提前记一句会改变看法的结果：例如新版少读了两篇文档，却让关键取舍晚到交付后才出现，那就保留旧做法。能决定保留、局部修改、继续试原型或回退时即可停止；两组无可辨别差异、又没有具体失败需要解释时，也可以收工。不要以读得少、消息少或用时短替代交付与体验判断。

下一次讨论只需要一个入口：最近哪一次你对 Agent 说“我的意思是……”，或者在看到成果后自然改变了主意？从那一句和它之后实际发生的事开始即可。若没有现成片段，就在下一次本来要做的工作里留意一次，无须先部署任何实验系统。
