    总的来说，想要正常使用 git，需要做一些配置：
      - 首先是安装 git 以及 ssh（因为很多时候我们都要用 ssh 来拉取或者上传仓库）
        #+begin_src bash
        sudo apt update
        sudo apt install git openssh-client
        git --version
        ssh -V
        #+end_src
      - 在正常输出 git 和 ssh 版本号以后，就可以开始下一步了。对 git 做一些简单的配置，--global 只作用于当前系统用户，不是整台机器。若使用的是多人共用的账号，不建议在里面配置个人长期凭据；署名也可在具体仓库内去掉 --global 单独设置。仅 clone／pull 不需要配置署名，commit 才需要
        #+begin_src bash
        git config --global user.name "你的名字"
        git config --global user.email "你的提交邮箱"
        git config --global init.defaultBranch main
        #+end_src
      - 配置好了以后，检查旧密钥，再生成服务器专用密钥（ssh key）
        #+begin_src bash
        ls -la ~/.ssh
        mkdir -p ~/.ssh
        chmod 700 ~/.ssh
        ssh-keygen -t ed25519 -C "server-git" -f ~/.ssh/id_ed25519_git
        #+end_src
        如果提示该文件已存在，别覆盖，换个名字。交互使用建议设置 passphrase（私钥口令）。生成后：
          - id_ed25519_git：私钥，留在服务器上，不要发给别人。
          - id_ed25519_git.pub：公钥，添加到 Git 平台。
      - 然后查看公钥，并复制它
        #+begin_src bash
        cat ~/.ssh/id_ed25519_git.pub
        #+end_src
      - 把公钥复制到: [[https://github.com/settings/keys][github keys]]
      - 然后测试一下 ssh
        #+begin_src bash
        ssh -T git@github.com
        #+end_src
        如果有了正确的返回，就说明配置成功了，之后可以使用 ssh 来对远端 github 进行一些操作，这样会更加稳定

      notes: 我尝试了一下静态链接和动态链接，并且理解了一下静态链接和动态链接的区别
        这里有几个我需要讲述的例子：首先是我的代码，我的结构是:
          #+begin_src bash
          .
          ├── foo.c
          ├── main.c
          └── Makefile
          #+end_src
        mian.c 的内容是:
          #+begin_src c
          #include <stdio.h>

          int foo(int n);
          int main(void) {
            int result = foo(100);
            printf("foo(100) = %d\n", result);
            return 0;
          }
          #+end_src
        foo.c 的内容是:
          #+begin_src c
          int foo(int n) {
          int sum = 0;
          for (int i = 0; i <= n; i++) {
            sum += i;
          }
          return sum;
        }
          #+end_src
        如果此时直接编译 main.c，使用命令 ~gcc main.c~ 将会得到一个错误:
          #+begin_src                                                                                                                     gcc main.c                                                                                                                      /usr/bin/ld: /tmp/ccCI5ODc.o: in function `main':
          main.c:(.text+0xe): undefined reference to `foo'
          collect2: error: ld returned 1 exit status
          #+end_src
        直接编译 main.c 在链接阶段是拿不到 foo 这个函数的具体实现的，而要想成功实现必须要拿到 foo 函数的实现，这个实现在 foo.c 中
        那我们传参的时候将 main.c 和 foo.c 都作为参数传给 gcc，就可以成功编译:
          #+begin_src
          gcc main.c foo.c
          #+end_src
        然后就生成了一个 a.out，一个 ELF 文件，使用 ~file~ 命令可以看到这个文件的详细信息:
          #+begin_src
          file a.out
          a.out: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=
          93148bad4d02bdbba28e91f97fab71eaef633542, for GNU/Linux 3.2.0, not stripped
          #+end_src
        这是一个动态链接产生的 ELF 文件，并且这个链接的过程还是自动的
        我们只需要告诉 gcc 我们有两个文件是需要一起编译的，gcc 很智能地就发现了 foo 函数是需要链接的内容
        但是这个过程也可以手动完成，命令我们会这么写:
          #+begin_src bash
          gcc -c foo.c
          gcc -c main.c
          gcc main.o foo.o -o main
          #+end_src
        这样得到了 main 这个 ELF 文件，使用 ~file~ 命令检查属性，会发现他和 ~gcc main.c foo.c~ 所得到的 ELF 文件一样也是动态链接来的
        执行也能发现结果是正确的，说明 *自动链接和手动链接与动态链接和静态链接并不冲突，是两个维度*
        我们也可以试试静态链接
        自动静态链接就是：
          #+begin_src bash
          gcc main.c foo.c -static
          #+end_src
        还是通过 ~file~ 来查看属性
          #+begin_src
          file a.out
          a.out: ELF 64-bit LSB executable, x86-64, version 1 (GNU/Linux), statically linked, BuildID[sha1]=4576da3ac087f8f4fdc3c1938f2796b7b50f06d5,
          for GNU/Linux 3.2.0, not stripped
          #+end_src
        也可以手动：
          #+begin_src bash
          gcc -c main.c
          gcc -c foo.c
          gcc main.o foo.o -static
          #+end_src

        实际上 Makefile 就是帮助我们编译项目的，实际的项目大概不会这样简单，它有非常多的组件，还有各种依赖，如果还是一行一行命令地构建，人总会犯错而且也很难纠正
        使用 Makefile 可以简化这个过程，另外 Makefile 还有特别的优势：Makefile 真正不可替代的地方是依赖关系和增量构建，这个优势将会在后面体会
        我们的 Makefile 将会如此组织
          #+begin_src Makefile
          main: main.o foo.o
            gcc main.o foo.o -static -o main

          main.o: main.c
            gcc -c main.c

          foo.o: foo.c
            gcc -c foo.c
          #+end_src
        执行命令 ~make~ 即可，并且也还是可以用 ~file~ 命令来查看 ELF 文件的属性

      如果 Ubuntu 在安装 noctalia shell 之前额外折腾过开发环境什么的, 那安装 noctalia 的时候几乎肯定会缺少一些依赖, 其中有一个依赖则是 Ubuntu26.10 不兼容
      这个依赖是 libsodium23, Ubuntu26.10 上默认已经是 libsodium26 了, 直接使用 apt 找包和下载的时候, 是下不到 libsodium23 的
      但是不下载就没法解决 noctalia shell 的依赖问题, 不过好消息是 Ubuntu 的包基本都可以从网站上下载下来
      所以只需要去官网上找到 libsodium23 的包并且直接把 deb 文件下载下来, 然后本地 apt install deb 文件就行了
      在那之前可以用 ~sudo apt install --simulate~ 来确认一下会不会出问题, 没问题在使用 ~sudo apt install~ 安装 libsodium23
      安装好后也不必删除掉 libsodium26, 二者是可以共存的, 不过 ABI 大概是不兼容的.
      接下来是解决 dms shell 和 noctalia shell 并存的问题, 其实很简单, 就是直接把 dms 关掉就行了, dms kill 关掉 dms 并关掉 dms 的监控服务
      如果无法直接彻底关掉, 我建议直接 mask 掉 dms shell, 这样 log out 再 back in 就不会同时运行两个 shell 了.
      如果后续想从 Noctalia Shell 切换回 DMS Shell，需要先关闭 Noctalia，再恢复 DMS。
      首先检查 DMS 的 systemd 用户服务：
      #+begin_src bash
      systemctl --user list-unit-files | grep -i dms
      #+end_src
      如果之前使用了 =mask= 禁用 DMS，需要先解除屏蔽。假设对应服务是 =dms.service=：
      #+begin_src bash
      systemctl --user unmask dms.service
      systemctl --user enable --now dms.service
      #+end_src
      如果只是通过 =dms kill= 关闭 DMS，没有屏蔽 systemd 服务，则可以尝试直接运行：
      #+begin_src bash
      dms run
      #+end_src
      接下来还需要关闭 Noctalia 的自动启动。如果之前在 =~/.config/niri/config.kdl= 中配置了：
      #+begin_src kdl
      spawn-at-startup "noctalia"
      #+end_src
      就将其注释：
      #+begin_src kdl
      // spawn-at-startup "noctalia"
      #+end_src
      最后注销并重新登录 Niri，确认只有 DMS Shell 在运行。
      需要注意，DMS 的服务名称和启动命令可能随安装方式及版本变化，因此应以本机实际安装的服务和 =dms --help= 输出为准。如果此前屏蔽的是其他服务，也应解除对应服务的屏蔽。
